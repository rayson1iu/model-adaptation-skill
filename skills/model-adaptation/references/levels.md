# 分级执行与交付

`level` 表示本次适配工作的深度，不是问题严重程度、调度优先级或硬件等级。级别定义见 [技能入口](../SKILL.md#调用参数与适配级别)。记录目标级别与实际完成范围，保留阶段失败与证据缺口；不能因为资源不足或某阶段失败而自动降低目标级别。

## 开工前的最小依据

先从用户请求、项目规范和现有产物中查找，不要求用户重复提供已有信息。下表区分“能开始部分工作”和“能判定目标级别完成”；缺项只阻止依赖该项的正式实验或验收。

| 级别 | 开工前需明确的依据 | 暂缺时可以继续什么 |
| --- | --- | --- |
| P0 | 模型与工作区、目标 GPU、权重与真实输入；约定训练方案、数据、完成条件；项目约定的 reference 基线及精度门槛；端到端路径、剖析目标与测量口径。长时训练或跨服务器工作还需明确项目已有或本次约定的资源/时间额度。 | 检查项目与环境、定位入口、准备配置和短程诊断；不凭空决定训练规模，不将无基线测量判为精度通过。 |
| P1 | 模型与工作区、目标 GPU、权重与真实输入；可核实的参考 GPU 基线、配对输入、比较指标及门槛。微调仅在决定需要时补齐数据、方案和完成条件。 | 先做环境、权重与推理检查；基线或门槛缺失时可输出诊断结果，但不能判 P1 精度对齐通过。 |
| P2 | 模型名称或可定位的模型线索、目标平台、调研用途及可访问的资料来源。 | 先核对官方仓库、论文或模型卡；无法核实的条件列为资料缺口，不运行实验补齐。 |

已有授权和项目额度覆盖的工作直接推进。信息缺失且会改变训练范围、正式比较含义或资源投入时，仅澄清受影响的决定；其他可独立工作继续进行。

## P0：训练、推理、精度与端到端性能

先固定模型、目标 GPU、参考配置、数据、训练方案、比较对象、验收门槛和性能测量边界，再按 [验证与测量](validation.md) 执行。

- **训练**：执行项目或用户指定的训练方案，记录数据划分、训练范围、有效更新数、loss/指标、检查点及完成依据。训练可以是指定的微调方案，不默认等于从头预训练；训练一步或短程诊断不能代替已约定的训练验收。方案或数据缺失时先澄清，不自行猜测训练规模。
- **推理**：在目标 GPU 上完成真实输入的模型推理验证，保留输入、实际设备、命令、输出和结果检查。
- **精度对齐**：固定 reference/candidate 与容差，验证约定的推理输出；训练 loss、梯度或更新结果是否纳入对齐由项目验收方案决定，不能省略已有要求或自行扩大范围。缺基线或门槛时仅报告诊断结果。
- **端到端性能剖析**：覆盖约定的输入到最终可用输出或训练步骤边界，声明训练与推理哪些路径纳入验收。报告可复现的时延、吞吐、显存与测量条件；独立采集 trace，解释主要阶段、GPU 热点与瓶颈。正式性能测量和 profiler 采集分开，只有计时或 CPU trace 不能替代 GPU 性能剖析。

交付实验配置、原始日志、训练产物、推理结果、精度报告、性能报告及剖析证据，可合并到已有运行报告中。逐项判定训练、推理、精度和端到端剖析是否满足约定要求；只有必需项全部通过才能报告 P0 完成。剖析交付完成与性能达到目标分别判定：没有约定性能门槛时可完成剖析，但不能写成“性能达标”；已有性能门槛则仍须逐项验收。

## P1：推理与参考 GPU 精度对齐，按需微调

推理跑通与参考 GPU 精度对齐均为必需项，方法沿用 [验证与测量](validation.md)。参考 GPU 需明确型号、配置及证据来源；可使用可核实的已有基线产物，不要求为形式重新运行或连接另一台服务器。CPU 结果不能替代参考 GPU 基线。

微调为条件阶段。先根据用户要求、任务指标与现有证据，判断是否存在可通过微调改善的任务效果或领域适配需求；数值误差、驱动或算子问题先定位，不能用微调掩盖精度对齐失败。

| 判断 | 处理与记录 | 对 P1 验收的影响 |
| --- | --- | --- |
| 无领域适配或任务效果改进需求，推理与精度已经满足约定 | 记“本次不需要”，说明依据 | 微调不作为必需项 |
| 有明确微调需求，且数据、方案、指标和资源条件齐备 | 在已有授权范围内执行，复验推理、精度及适用的任务指标 | 若微调已列为本次验收项，复验通过才算完成 |
| 有微调需求但条件不足 | 记录缺口与下一步，不写成已完成 | 若微调已列为本次验收项，P1 保持未完成 |
| 精度对齐失败且根因尚未定位 | 先定位数值、算子或配置差异 | 微调不能替代精度对齐通过 |

交付推理和精度对齐证据，以及微调的决策、依据、执行结果或条件缺口。P1 不自动要求 P0 的训练与端到端性能剖析，也不自动加入闭环或跨服务器实验。

## P2：调研收录，仅技术报告

读取必要的项目背景、模型官方仓库、论文、模型卡和框架文档。查询可访问的权威来源，记录链接、版本或提交、发布日期（可得时）和调研日期。来源不可访问或内容不能核实时明确列为缺口，不以推测补全。

P2 不修改模型源码或执行环境，不安装依赖、创建容器、下载权重/数据集，不运行模型或实验；仅输出技术报告，不额外创建实验配置、运行报告、工作日志或 ISSUE。“收录”在本级别体现为报告中的模型条目与收录建议；只有用户另外要求时才更新外部模型登记。

技术报告面向需要决定是否收录和投入适配的读者，先给出明确建议和两三条关键理由，再按以下内容展开；优先沿用项目现有报告版式，没有等价模板时使用[技术调研报告模板](../assets/research-report.md)。

1. **模型概览**：名称、用途、架构、上游版本与许可证；架构或推理路径较复杂时用简图说明。
2. **落地条件**：权重、依赖、支持精度、训练/推理入口、硬件与资源要求。用紧凑表格呈现关键条件。
3. **适配判断**：目标平台的可行性、主要框架/算子/精度/资源风险，以及对后续 P1/P0 工作量的影响。
4. **建议与下一步**：是否建议收录、优先解决的问题、升级到 P1/P0 的路线和前置条件。
5. **资料与边界**：附上来源链接、版本或提交、调研日期及关键证据缺口；明确“本次仅调研，未执行新实验”。

图表只在能帮助读者理解架构、依赖关系或风险排序时使用。引用历史测试或上游指标时保留原条件和出处，与本次分析清楚区分；将一般性的来源说明集中在资料部分，避免反复打断正文结论。

## 分级验收判定

每个必需阶段在报告中单独记录“通过、失败、被阻塞、未验证”；不适用仅用于条件阶段或明确不在本次范围内的项目，不能代替必需项。以下是最小完成证据，详细测量方法见[验证与测量](validation.md)。

| 级别与阶段 | 可判为通过的最小证据 |
| --- | --- |
| P0 训练 | 按冻结方案实际完成约定更新/周期与检查点，保留训练日志及约定的完成指标；单步诊断不算。 |
| P0/P1 推理 | 目标 GPU 上的真实输入、实际设备、命令、输出及结果检查可复核。 |
| P0/P1 精度对齐 | 可核实的约定 reference 基线、配对输入、冻结门槛、逐样本与汇总结果支持通过；P1 的 reference 必须是参考 GPU。 |
| P0 端到端性能剖析 | 测量边界与条件明确，有正式计时数据、独立 GPU trace、阶段/热点分析和瓶颈结论；有约定性能目标时另判是否达标。 |
| P1 条件微调 | 先有是否需要的判断；若列为本次验收项，按约定方案执行并复验相应指标。 |
| P2 技术报告 | 有明确收录建议、主要依据、适配风险、下一步和可追溯资料；结论只代表调研，不代表实测通过。 |

汇总状态按目标级别判断：全部必需项通过为“通过”；任一必需项实测失败为“失败”；没有失败但必需项因外部条件无法执行为“被阻塞”；有未执行/未验证必需项或用户裁剪了必需范围为“部分完成”，尚无可判断结果时为“未验证”。报告可以另写已完成的局部成果，但不得用局部通过替代目标级别通过。任务约定的性能目标、微调或其他验收项同样纳入汇总；只有剖析而没有性能门槛时，不声称性能达到目标。

## 范围与验收记录

P0/P1 在实验配置与报告中记录 `level`、实际范围、适用门槛与逐项状态。用户明确排除某必需阶段时，按用户的具体限制执行，标记范围裁剪；出现无法判断的矛盾时仅澄清受影响部分，不启动有争议的工作。

P2 的完成标准是技术报告按范围交付并清楚标出依据与缺口，不是适配通过。未指定 `level` 的任务继续按自然语言范围处理，不强行归级。
