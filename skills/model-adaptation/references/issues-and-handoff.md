# 问题记录与交接

## 发现、修复和复验

值得持续跟踪的问题可沿用项目的 ISSUE 流程。简单修复可在工作日志中说明。单纯因网络导致的下载失败不建 ISSUE，有必要时把影响和恢复方式记入工作日志或交接说明。

记录问题时，先说清触发条件、预期、实际现象和影响，附关键证据。区分已确认的事实和待验证的原因。精度问题可并列给出基线、候选及可比条件。修复后说明实际复验覆盖的范围和剩余问题。[ISSUE 模板](../assets/issue.md)

### 兼容性问题分级与归因

P0 和 P1 遇到兼容性问题时，优先沿用项目分级。没有既有标准时，可按实际影响判断严重程度。

- **阻塞**。核心训练或推理路径无法执行，且暂无可用绕行方案。
- **严重**。核心路径可以运行，但关键精度或性能目标未达标，或绕行方案显著影响任务效果或资源开销。
- **一般**。影响局限于特定配置或非关键路径，主要目标仍可达到。

先用最小复现确认触发条件，再根据证据检查平台依赖、框架、算子、精度或模型配置。可通过替换单个变量、对照参考卡或检查 trace 缩小范围。记录已确认的原因和仍待验证的假设。

## 运行与持续记录

选择对复现、排错和接手有用的内容记录。一次有意义的运行通常可从命令或入口、实际配置、结果和日志定位。长时后台任务可补充进程标识、当前阶段和恢复入口。交接时以最新日志和实际产物为依据，把运行结束和验收通过分别表述。[工作日志](../assets/work-log.md)

## 历史复核

用原始产物、当时的配置和已有摘要核实结论。缺失版本、命令或输入时，说明对判断或复现的影响。把历史证据和本次观察明确标记。

## 交付核对

让接手者能从当前结论找到证据、看懂失败或阻塞范围，并知道接下来做什么。若项目维护模型登记、问题索引或汇总页，按实际影响更新。ISSUE 默认用文字和表格，只有用户明确要求时才画图。
